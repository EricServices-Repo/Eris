# Eris v1.0.1 production release coding checklist

**Document status:** proposed release acceptance plan; **not a release certification**.
**Reviewed:** 2026-11-01. **Source baseline:** integrated `origin/main` at `b59c766b9801ceef0ac851c27c3d986f0e5cc698`; desktop package `0.6.10`.
**Target:** `1.0.1` for the production Eris IDE and the corresponding Eris-Dev debug application. This document does not bump versions, build binaries, publish a release, or authorize merging changes.

The checklist contains **225 coding/acceptance obligations, 40 regression scenarios, and 9 final signoffs** (274 unchecked items).

This is a checklist of engineering work and proof needed for a production release. It covers chat → agent, agent → agent, agent → model, RAM context, tools, editor, debugging, diagnostics, desktop distribution, and recovery. It is intended for maintainers and coding agents working through small, independently reviewable changes.

All boxes start unchecked. An implemented safeguard still needs evidence on the release candidate. An unchecked box is **not** a finding that the code is defective. This review inspected source, architecture/design guides, test profiles, CI/release workflows, and the current GitHub issue inventory; it did not execute a new release qualification run. Historical passing test totals must not be reused as v1.0.1 certification.

## Completion rules and release blockers

### How to complete an item

Each stable ID is a separate acceptance obligation. Before checking it, attach a PR/commit or a documented source review, a regression test or reproducible acceptance procedure, the exact candidate source SHA, its result, and an accountable reviewer. The owner listed for a section is a role to assign to a person, not an assignment that has already been made.

Use the following work states in the issue or evidence ledger:

- **VERIFY:** implementation exists or may exist; establish its behavior on the candidate. Do not rewrite working code simply because this box is unchecked.
- **BUILD:** implement or extend a missing capability/test boundary identified in this plan.
- **DECIDE:** explicitly select supported scope, limits, or feature enablement. A decision must produce enforced product behavior and matching documentation.
- **OPERATE:** collect platform, distribution, security, or release evidence that source inspection cannot establish.

An item can close as `passed`, `implemented-and-passed`, or `disabled-and-verified` when its conditional scope permits disabling. A deferral must name the feature removed from v1 scope, prove it is inaccessible through UI, IPC, tools, persisted jobs and APIs, remove unsupported promises, and link its follow-up issue. A hidden control alone is not sufficient. Mandatory authority, privacy, data integrity, core chat/coding, cancellation and release-certification gates cannot be waived by a generic risk acceptance.

### Release severity

- **P0 / stop ship:** unauthorized effects or disclosure; corruption/loss of user work; uncontained worker/command execution; a release known to contain exploitable shipped credentials; false success after failed mutation; broken install/update; bypassed 1.x certification.
- **P1 / required core:** reliable task intake, follow-ups, implementation requests that actually edit, eligible model dispatch, bounded recovery, durable visible task outcomes, usable chat/editor/settings, reproducible CI and supported hardware behavior.
- **Conditional:** Cloud execution, image generation, broad specialist memory inheritance, automatic large RAM tiers, semantic embeddings, cross-turn KV reuse, and other unqualified extensions may be deferred only through the disabling process above. Enabled features must pass their applicable gates.
- **Optimization:** improve measured resource cost or latency without weakening correctness. No unmeasured rewrite is automatically required for v1.

**Production completion means:** all applicable obligations are evidenced; all known P0/P1 core defects are fixed; disabled features are honestly scoped; exact-source CI, packaged interaction, real-model, hardware, installer and update evidence passes; support/rollback owners approve the release. Passing a scripted 10,000-question corpus alone is insufficient.

## Baseline and current gaps

### Existing foundations to preserve and recertify

The integrated baseline includes typed task contracts; explicit model locality/pinning policies; tool schemas and effect admission; measured native context checks; request-scoped recall and pre-dispatch revalidation; bounded handoff envelopes; persisted task-tree limits; context-origin seals; typed child outcome integration; stable-prefix prompt assembly; memory diagnostics; and separate Eris-Dev qualification profiles. These are not all missing features.

Recent merged work that must be included in candidate regression coverage:

- #235 contextual follow-up recall and #236 memory-tier diagnostics.
- #263 host-sealed context origin and #264 typed, idempotent child outcome integration.
- #232 stable-prefix ordering (`model-task/4`), with real conversation roles and volatile current-turn context separated.
- #256 persisted evidence revalidation; #259 final dispatch revalidation; #260 required prompt-fit refusal; #262 persisted subtree budgets; #265 bounded handoff envelopes.

These IDs identify implementation history, not permission to skip candidate tests. A source receipt is not proof of a correct answer; stable prefix ordering is not proof of a native KV-cache hit; a context-origin seal is not unrestricted parent-memory inheritance.

### Known release preparation gaps

The 12 open issues captured for this review are listed below. They include trackers, capability gaps and measurement hypotheses; they are not 12 reproduced runtime defects. The architecture drafts and recommendation ledgers may describe older source revisions. Reconcile them against the candidate instead of copying their old status labels.

Important source-confirmed limits:

- The RAM context singleton remains in Electron main; current limits are bounded MiB-scale settings, not an implemented multi-GiB dedicated memory process.
- Run journals are run-local; durable post-run tool-result recall remains separate work.
- Cross-turn native KV reuse/parking and CPU embedding recall are not established shipped capabilities.
- Context hardware release profiles in `checks/performance/context-budgets.json` are currently **empty**. Strict release qualification requires hardware-matched profiles, so the current file is not sufficient to certify v1.0.1.
- Cloud advertises task-contract v1 while the desktop uses v2; do not advertise compatible v2 remote execution without conformance work.
- The packaged production smoke checks startup/preload/isolation, not the complete installed chat → approval → mutation → diff → reload journey.
- Eris-Dev pinned-model runs do not by themselves exercise production Auto-local selection or switching.
- Release workflows can currently build unsigned artifacts when certificates are absent. This is not evidence of signed/notarized production distribution.

The source of truth for current architecture is the candidate code plus executable tests. Use [the architecture index](README.md), [architecture](ARCHITECTURE.md), [handoff/RAM design](design/AGENT-HANDOFF-AND-RAM-CONTEXT.md), [model execution](design/AUTO-MODEL-EXECUTION.md), [RAM architecture](RAM-CONTEXT-ARCHITECTURE.md), [RAM amendment](RAM-CONTEXT-AMENDMENT-001.md), and [recommendations](RECOMMENDATIONS.md) for context. ## Coding and acceptance checklist

### REL. Release scope, compatibility and repository discipline

**Accountable role:** Release lead. **Code/evidence anchors:** [package.json](../package.json), [GitHub workflow](GITHUB-WORKFLOW.md), [release source resolver](../scripts/release-source.cjs).

- [ ] **REL-01 — Freeze the v1 product contract** (DECIDE). Write the supported macOS/Windows versions, CPU architectures, GPU backends, local/remote providers, agent modes and shipped optional capabilities. Every advertised capability must map to an acceptance scenario and an owner; anything excluded must have explicit product gating.

- [ ] **REL-02 — Define v1.0.1 compatibility** (DECIDE). State which 0.6.x installations, database/settings versions, model directories, credentials and task records can upgrade. Define downgrade limitations and backup behavior before changing any persisted schema.

- [ ] **REL-03 — Use isolated change branches** (VERIFY). Keep each implementation on a feature branch, with an issue and PR into the currently approved integration branch. Do not directly push to protected main/dev, rewrite unrelated local work, or assume an old branch policy overrides current repository configuration.

- [ ] **REL-04 — Reconcile architecture against the candidate** (VERIFY). Update baseline SHAs and implemented-versus-proposed status in architecture, RAM, handoff, recommendations and usage guides. Remove claims now fixed by merged work and claims that still exceed implemented behavior; preserve dated historical evidence as historical.

- [ ] **REL-05 — Maintain an owned release ledger** (DECIDE). Create an issue or machine-readable ledger mapping every ID in this document to owner, state, PR, evidence and dependencies. A tracker issue is not an implementation unit; split changes when ownership or failure boundaries differ.

- [ ] **REL-06 — Version all distribution identities coherently** (VERIFY). At release preparation, set production and Eris-Dev display/package versions, lockfile metadata, installer names and updater metadata to the approved version. Independently version protocol/schema contracts; a package bump must not silently redefine them.

- [ ] **REL-07 — Bind builds to immutable source** (VERIFY). Resolve the release tag, source commit and lockfile identity before compiling. Reject mismatches and ambiguous repair requests; rebuilding an asset must not move an existing tag or silently build the working checkout instead.

- [ ] **REL-08 — Establish candidate freeze and requalification rules** (OPERATE). Record the RC SHA and affected evidence dependencies. A code, model, runtime, lockfile, packaging or security-policy change invalidates the relevant evidence; never carry a green result across a changed boundary without documented analysis and rerun.

### INT. Chat intake and task interpretation

**Accountable role:** Agent orchestration maintainer. **Code/evidence anchors:** [chat IPC](../electron/main/ipc/chat-stream.ts), [task contract](../src/shared/task-contract.ts), [task resolver](../electron/main/services/task-resolver.ts), [intake tests](../tests/chat-admission.test.ts).

- [ ] **INT-01 — Validate every inbound message at the boundary** (VERIFY). Reject malformed, oversized, empty or unauthorized chat submissions before allocating a task or opening a provider stream. Validate thread/workspace identity, attachments and selected controls in main rather than trusting renderer payloads.

- [ ] **INT-02 — Preserve the actual user request** (VERIFY). Keep the latest instruction, relevant follow-up references and requested deliverable intact through routing and prompt compilation. Test that status strings, pasted transcripts and tool results cannot replace the current request or become higher-priority instructions.

- [ ] **INT-03 — Separate advice from authorized implementation** (VERIFY). Review-only requests must stay read-only. An explicit follow-up such as “add those improvements to the code” must produce an editing contract with the prior recommendations carried forward, rather than retaining a Reviewer prohibition on edits.

- [ ] **INT-04 — Handle ordinary conversation without workspace mutation** (VERIFY). Stories, explanations, brainstorming, design discussion and simple answers must reach an eligible chat model without forced tree/read/write sequences. Test Auto with no workspace and with an unrelated open repository.

- [ ] **INT-05 — Resolve the correct project and artifact** (VERIFY). Honor the user's selected workspace and explicit paths. If an AirBNB task is issued while a calculator project is open, gather real evidence and report the mismatch instead of modifying an unrelated App.js or inventing PHP files.

- [ ] **INT-06 — Carry explicit acceptance obligations** (VERIFY). Represent requested artifact, destination, change scope, constraints and success conditions in the task contract. Verify these obligations survive routing, delegation, model adaptation and completion checking without being diluted into a vague task summary.

- [ ] **INT-07 — Interpret ambiguous follow-ups using bounded history** (VERIFY). Resolve “those changes,” “continue,” and “what changed” against eligible recent conversation evidence. Ask a focused question only when the ambiguity materially affects action; never fabricate an earlier recommendation or use another thread as authority.

- [ ] **INT-08 — Enforce send admission and deduplication** (VERIFY). Repeated clicks, retried IPC, rapid follow-ups and renderer reloads must not start duplicate mutation runs. Give each accepted send a stable identity and explicit queued/running/rejected state, and report the same admission result on safe retry.

- [ ] **INT-09 — Preserve steering and queued messages** (VERIFY). Define whether a new message steers, queues behind, or cancels a running task; preserve its text and attachments durably. Tests must show that new user constraints reach the correct execution before subsequent effects are admitted.

### RUN. Agent execution, progress and completion

**Accountable role:** Agent runtime maintainer. **Code/evidence anchors:** [agent loop](../electron/main/services/agent/loop.ts), [workflow](../electron/main/services/agent/workflow.ts), [recovery](../electron/main/services/agent/recovery.ts), [task outcome](../electron/main/services/task-outcome.ts).

- [ ] **RUN-01 — Use explicit lifecycle state** (VERIFY). Keep admitted, queued, preparing, executing, awaiting approval, verifying, complete, cancelled and failed states distinguishable. Every terminal state must be reachable exactly once with a durable reason and all owned resources released.

- [ ] **RUN-02 — Detect progress from evidence** (VERIFY). A changed file, new source evidence, completed check or resolved obligation counts as progress. Reworded plans, identical tool calls and status spam do not; tests must prevent both infinite loops and premature stopping after legitimate multi-step inspection.

- [ ] **RUN-03 — Make recovery bounded and useful** (VERIFY). Limit retries and adaptations by root-run budget and deadline. Preserve successful work, select a genuinely different eligible recovery path when permitted, and return a concrete blocker when no actionable next step exists.

- [ ] **RUN-04 — Prevent advice-only completion of coding tasks** (VERIFY). For a mutation contract, require effect evidence or an explicit no-change justification grounded in the code. A paragraph saying “modify these files” must not satisfy “make these improvements”; independently inspect resulting changes and verification status.

- [ ] **RUN-05 — Handle partial success honestly** (VERIFY). If edits succeeded but tests failed, persistence failed or the run exhausted its budget, report applied changes and the unresolved failure separately. Never replace a partial result with a generic success sentence or claim all changed files are verified.

- [ ] **RUN-06 — Make cancellation interrupt every wait** (VERIFY). Stop must cancel queued inference, model loading, streaming, approvals, commands, child agents and retry timers. Late chunks or child completions must not revive a cancelled run or overwrite a newer chat answer.

- [ ] **RUN-07 — Retain artifact-aware completion validation** (VERIFY). Use appropriate checks for code, design documents, stories and image requests. Generated code should receive syntax/type/build checks when meaningful; a prose task must not be judged solely by file mutations or by the agent's own success claim.

- [ ] **RUN-08 — Create deterministic lifecycle transition coverage** (BUILD). Extend tests so every state transition, timeout and persistence failure is exercised through the actual runtime boundary. If extracting a reducer/kernel, prove event ordering, effect ownership and compatibility before replacing the existing loop.

- [ ] **RUN-09 — Expose actionable stop reasons** (VERIFY). Differentiate user cancellation, missing capability, model protocol failure, exhausted recovery, approval denial, context overflow and environmental failure in typed results. The chat must explain what happened and what remains without requiring users to decipher internal log fragments.

### A2A. Delegation, context ownership and child integration

**Accountable role:** Multi-agent/context maintainer. **Code/evidence anchors:** [background agents](../electron/main/services/background-agents.ts), [context origin](https://github.com/EricServices-Repo/Eris/blob/b59c766b9801ceef0ac851c27c3d986f0e5cc698/electron/main/services/context-origin.ts), [child outcome](https://github.com/EricServices-Repo/Eris/blob/b59c766b9801ceef0ac851c27c3d986f0e5cc698/electron/main/services/child-outcome.ts), [handoff tests](https://github.com/EricServices-Repo/Eris/blob/b59c766b9801ceef0ac851c27c3d986f0e5cc698/tests/handoff-envelope.test.ts).

- [ ] **A2A-01 — Retain a validated handoff envelope** (VERIFY). Validate required contract, scope, parent/root identity, evidence and budget fields at tool admission, enqueue and durable reload. Oversized required fields must fail explicitly; any shortened optional fields need bounded omission metadata.

- [ ] **A2A-02 — Keep delegated authority narrower than the parent** (VERIFY). A child may receive only the tools, paths, effects, destinations and budget needed for its task. It cannot convert a review into a write, broaden provider disclosure, or infer authority from parent prose or role names.

- [ ] **A2A-03 — Validate source identity independently of execution identity** (VERIFY). Verify host-sealed ContextOrigin binding, profile, source namespace/project, epochs and execution binding. Reject tampered, cross-profile, stale or incorrectly rebound handles, including after worktree changes and Windows path normalization.

- [ ] **A2A-04 — Revalidate evidence after parent completion** (VERIFY). Persist enough source/version/disclosure metadata to check delayed children after the original request lease ends. A closed parent lease must not make valid evidence unusable or make expired evidence automatically trusted.

- [ ] **A2A-05 — Enforce subtree-wide budgets after restart** (VERIFY). Retain depth, total children, aggregate work and deadline limits across enqueue/reload/recovery. Recursion, duplicate tasks and agent/goal cycles must fail predictably; fresh child counters must not reset a root's budget.

- [ ] **A2A-06 — Cancel and drain the whole subtree** (VERIFY). Cancel descendants, commands and queued inference when the root is cancelled or its workspace closes. Ensure completion messages from a draining child cannot apply a result after cancellation, approval revocation or deadline expiry.

- [ ] **A2A-07 — Integrate typed child outcomes exactly once** (VERIFY). Require child identity, result revision, evidence, actual effects, check results and unresolved obligations. Repeated delivery/reload must not duplicate canonical chat receipts; failed or unapplied prose cannot become a verified integrated change.

- [ ] **A2A-08 — Detect integration conflicts and stale checks** (VERIFY). Compare source hashes before applying child results, preserve unrelated user changes and reject stale bases. Checks run before a merge remain historical until rerun on integrated output; execution success and integration success remain separate fields.

- [ ] **A2A-09 — Qualify isolated multi-agent replay** (BUILD). Implement the production task-tree boundary in Eris-Dev/CI for #267 using temporary projects and no inherited user secrets. Replay parent recall, child evidence pulls, privacy changes, cancellation, restart and result import with deterministic failure injection.

- [ ] **A2A-10 — Resolve the specialist context-handle scope** (DECIDE). For #151, either implement source-scoped, read-only handles with lifetime/disclosure controls or explicitly limit specialist inheritance to the validated evidence already supported. Never copy the entire parent transcript or promise full RAM sharing from an origin seal alone.

### MOD. Model eligibility, routing and switching

**Accountable role:** Model orchestration maintainer. **Code/evidence anchors:** [model destination](../electron/main/services/model-destination.ts), [model transition](../electron/main/services/agent/model-transition.ts), [Auto policy tests](../tests/auto-model-policy.test.ts), [switching tests](../tests/model-switching.test.ts).

- [ ] **MOD-01 — Keep agent role separate from model policy** (VERIFY). Auto agent selection, Composer/Coder/Reviewer roles and Fixed/Auto-local/Auto-any model policies must remain independent controls. Persist and display the effective combination so a role change cannot silently change privacy or model pinning.

- [ ] **MOD-02 — Evaluate eligible installed models before Lite fallback** (VERIFY). Discover and validate ready models, capabilities and resource eligibility before defaulting to Composer Lite. A locally installed capable model must not be ignored because of stale renderer catalog state, startup order or a different application profile.

- [ ] **MOD-03 — Filter locality before scoring** (VERIFY). Under Local policy exclude remote destinations before ranking, including LAN endpoints treated as remote by the policy. Consent for recalling text is not consent to send it to another endpoint; explicit remote mode must still pass disclosure checks.

- [ ] **MOD-04 — Honor fixed model selection** (VERIFY). A pinned model must remain pinned across retries, delegation where promised, protocol fallback and context pressure. If it cannot execute the task, report why or obtain a permitted policy change; do not silently substitute another provider.

- [ ] **MOD-05 — Calibrate task capability honestly** (VERIFY). Separate known capabilities, observed qualification and heuristics. Rank editing, tool use, structured output and long-context tasks using applicable fingerprinted evidence; unknown or stale scores must not masquerade as measured capability.

- [ ] **MOD-06 — Perform a real coordinator-to-worker transition** (VERIFY). When Lite delegates execution, invoke the chosen eligible worker with the same task obligations, safe context and owned lease. A log announcing a handoff without a different actual model dispatch must fail the test.

- [ ] **MOD-07 — Use a different eligible recovery model** (VERIFY). Track attempted model identities and failure reasons within the run. Recovery must not repeatedly pick the same failing model under a different label; enforce bounded adaptations and never route around an authority or safety refusal.

- [ ] **MOD-08 — Preserve policy across asynchronous switches** (VERIFY). Before the next provider call, recheck model readiness, destination, current privacy controls, measured prompt fit and resource ownership. A queued switch must not send stale recalled text after a forget/revoke action.

- [ ] **MOD-09 — Measure production Auto separately from pinned inference** (BUILD). Add a debug/qualification mode that exercises the production selector and switch path with a controlled catalog. Keep this separate from pinned-model benchmarking; record candidate eligibility, selected identity, exclusions and actual dispatched identity.

### WIRE. Prompt compilation and provider protocol

**Accountable role:** Inference protocol maintainer. **Code/evidence anchors:** [context compiler](../electron/main/services/agent/context-compiler.ts), [protocol](../electron/main/services/model-protocol.ts), [measured context](../electron/main/services/agent/measured-context.ts), [request invariants](../electron/main/services/agent/request-invariants.ts).

- [ ] **WIRE-01 — Preserve trust and role boundaries on the wire** (VERIFY). System/project instructions, real user turns, assistant turns, tool calls/results and untrusted retrieved content must serialize with correct roles. Pasted logs, code comments and web pages cannot acquire instruction authority through concatenation.

- [ ] **WIRE-02 — Retain stable-prefix ordering** (VERIFY). Test model-task/4 stable instructions/project prefix, prior conversation roles and volatile current-turn layers. Record an estimated prefix separately from provider/native cached-token measurements; changing order must not weaken required-context admission priority.

- [ ] **WIRE-03 — Budget the complete provider payload** (VERIFY). Count or conservatively reserve model framing, tool schemas, native protocol overhead and answer capacity, not just visible message characters. Cover multibyte text, large schemas and providers with different context accounting.

- [ ] **WIRE-04 — Measure the first native allocation before dispatch** (VERIFY). After a cold load, validate the actual allocated window against the required prompt and output reserve. If the native runtime allocated less than requested, recompile safely or fail explicitly; never trim required user instructions silently.

- [ ] **WIRE-05 — Revalidate immediately before provider send** (VERIFY). After all asynchronous preparation, confirm contract, source versions, privacy policy, selected destination and active resource lease. Test revocation, model switch and workspace close during model load and just before the transport opens.

- [ ] **WIRE-06 — Validate tool call/result pairing** (VERIFY). Require unique call IDs, valid schemas and complete result pairing across native and text-tool protocols. Reject malformed mixed output, duplicate IDs and unmatched results without executing invented calls or losing already observed effects.

- [ ] **WIRE-07 — Bound protocol repair** (VERIFY). Handle malformed JSON/tool syntax with a finite repair policy that cannot duplicate writes. A structured-output fallback must retain the same authorization, required context and destination rather than rebuilding a permissive generic prompt.

- [ ] **WIRE-08 — Normalize streaming and finish reasons** (VERIFY). Cover partial UTF-8, chunk boundaries inside JSON, reasoning/content separation, finish-with-tool-call, provider errors and truncated output. Exactly one final result must reach the right run after cleanup, including when usage arrives late.

- [ ] **WIRE-09 — Qualify each advertised backend** (VERIFY). Run conformance fixtures against native GGUF, supported loopback services and enabled remote APIs. Provider-specific adapters need explicit capability/timeout/error behavior; an OpenAI-compatible label is not proof of identical semantics.

### RAM. RAM store, canonical history and privacy

**Accountable role:** Memory/storage maintainer. **Code/evidence anchors:** [context store](../electron/main/services/context-memory-store.ts), [memory service](../electron/main/services/context-memory.ts), [dispatch guard](../electron/main/services/memory-dispatch.ts), [memory tests](../tests/context-memory.test.ts).

- [ ] **RAM-01 — Keep durable history authoritative** (VERIFY). Treat RAM as a bounded cache, not the only transcript. Cold cache, eviction, restart and worker failure must recover eligible canonical records without losing messages or fabricating a complete cache from a partial page.

- [ ] **RAM-02 — Preserve namespace isolation** (VERIFY). Separate profile, project, thread, source epoch and execution identity. Test same-named projects, renamed worktrees, reopened paths, symlinks and Windows casing; no memory may leak merely because labels or relative filenames match.

- [ ] **RAM-03 — Respect control sequences and exclusions** (VERIFY). Forget, clear, retention cutoff, disabled recall and remote-disclosure changes must affect search, compilation, context pulls and delayed children. Add race tests where controls change after selection but before actual provider send.

- [ ] **RAM-04 — Account reservations before allocation** (VERIFY). Bound encoded segments, decoded reads, search scratch, pending hydrations and metadata before allocating them. Failed admission/cancellation must release reservations; configured logical bytes must not be presented as whole-process RSS.

- [ ] **RAM-05 — Keep the send path bounded** (VERIFY). Do not scan the entire archive, synchronously summarize a long chat or allocate a full transcript on every send. Establish timeout/fallback behavior for cache hydration and optional recall so memory enrichment cannot stall a basic chat indefinitely.

- [ ] **RAM-06 — Test pressure-induced degradation** (VERIFY). Exercise shrinking budgets, simultaneous workloads, background indexing and low free memory. Evict optional recall before required task context, preserve canonical source data, and report pressure omission distinctly from “no relevant memory.”

- [ ] **RAM-07 — Qualify contextual follow-up recall** (VERIFY). Cover primary query terms, active-file hints, prior recommendations and the latest eligible user intent. Expansion must remain bounded and lower priority, exclude forgotten/other-project rows, and avoid logging private expanded text.

- [ ] **RAM-08 — Validate inspector numbers and controls** (VERIFY). Show configured budget, logical retained bytes, current native window, estimated KV, actual device classification and historical samples with clear units. Unavailable measurements must show unknown; switching chats must not display another thread's private source details.

- [ ] **RAM-09 — Resolve dedicated memory-process scope before increasing limits** (DECIDE). For #228, implement bounded off-heap segments/IPC/crash recovery before enabling multi-GiB retention, or retain current safe limits and remove large-tier claims. A worker extraction must preserve source authority, reservations, revocation and foreground responsiveness.

- [ ] **RAM-10 — Resolve hardware-aware tier sizing** (DECIDE). For #227, derive optional RAM from measured headroom and dedicated versus unified memory, with hard ceilings and manual override. If deferred, keep conservative settings and truthful diagnostics; never apply a dedicated-GPU formula to shared Metal memory.

### REC. Recall, journal durability and compaction

**Accountable role:** Context retrieval maintainer. **Code/evidence anchors:** [run journal](../electron/main/services/agent/run-journal.ts), [context pulls](../electron/main/services/agent/context-pull.ts), [compaction](../electron/main/services/agent/compaction.ts), [tiered gates](../checks/tiered-gates.ts).

- [ ] **REC-01 — Keep compacted evidence addressable** (VERIFY). When tool output is removed from the prompt, retain valid bounded references while the run remains active. Verify exact bytes can be recovered through the model-visible reference after repeated compaction; a list of hidden test-side entries is weaker proof.

- [ ] **REC-02 — Distinguish pull outcomes** (VERIFY). Return found, unknown, expired, omitted, denied and temporarily busy outcomes consistently. The model must not interpret unavailable evidence as proof a file or fact does not exist, and the caller must be able to retry only retryable failures.

- [ ] **REC-03 — Bound context_search and context_read** (VERIFY). Enforce per-call output, decoded bytes, search scratch, source scope and deadline limits. Test hostile repeated searches and oversized reads; requested byte ranges must not bypass journal/global memory admission.

- [ ] **REC-04 — Resolve post-run journal retention** (DECIDE). For #225, either persist indexed evidence with explicit retention, checksums, crash recovery and deletion controls or document that run-local refs expire. Do not claim later chats can recover arbitrary historical tool output from final prose alone.

- [ ] **REC-05 — Resolve source-backed summaries** (DECIDE). For #150, qualify summaries as derived, revocable, source-linked evidence generated off the send path. If omitted, retain bounded lexical recall; never erase original eligible records or let stale summaries resurrect forgotten content.

- [ ] **REC-06 — Resolve approved project facts** (DECIDE). For #152, require user approval, source/owner attribution, versioning, deletion and provider disclosure controls. Default to thread isolation; inferred facts or successful child results must not become shared project memory automatically.

- [ ] **REC-07 — Evaluate optional CPU embeddings** (DECIDE). For #234, compare lexical and embedding retrieval on frozen labeled queries, including paraphrases and privacy controls. Enable only with bounded CPU/RAM/index cost, explicit model download and deletion semantics; zero VRAM usage must be measured rather than assumed.

- [ ] **REC-08 — Evaluate KV reuse and parking** (DECIDE). For #233, prove native runtime support, stable-prefix identity, per-thread isolation, invalidation and memory accounting before retaining sessions across turns. Keep current per-run sessions if no measured gain; never restore forgotten content through a parked KV cache.

### TOOL. Tool lifecycle, effect authority and output handling

## Required scenario matrix

Use stable fixtures and record the stages actually exercised: `unit`, `production-boundary replay`, `packaged UI`, `live model`, `hardware`, or `installed/update`. Not every scenario requires a paid model call; no unit result may be relabeled as installed/live evidence. All applicable authority/privacy failures must be zero, including in negative cases.

### Task understanding and useful outcomes

- [ ] **SCN-01 — Story through Auto:** ask for a story with no repository, then with an unrelated repository open. Receive the requested story; no forced workspace edit, tool loop or “coding only” refusal.
- [ ] **SCN-02 — Review then implement:** review a fixture AirBNB app for three improvements, then say “add those improvements.” Preserve the recommendations, switch to authorized editing, change the correct files and report actual verification.
- [ ] **SCN-03 — Review-only safety:** request a review and suggestions without implementation. Read relevant sources, cite real paths and make zero filesystem mutations.

## Commands and evidence boundaries

These commands are an evidence plan, not a record that they were executed for this document. Run them from the exact candidate checkout on the platform required by the command, using committed dependencies and an isolated acceptance profile where applicable. Native compilation may require platform toolchains. Avoid concurrently running suites that mutate shared generated output or own exclusive test resources.

### Install, static checks and deterministic suites

```sh
npm ci
npm ci --prefix cloud-agent --ignore-scripts
npm run typecheck
npm run lint
npm run typecheck --prefix cloud-agent
npm test
npm run test:agents
npm run test:dev-app
npm run test:smoke:chat
npm run check:capabilities
npm run check:client
npm run check:accessibility
npm run check:ux
npm run check:context
npm run check:performance
npm run check:quality
npm run check:recovery
npm run audit:security
```

- `npm ci` and the lockfiles establish installation reproducibility; network ECONNRESET must be recorded as an install failure, not a source regression or a successful test run.
- `npm test` prepares the owned-command helper through its lifecycle script. Calling an individual underlying runner may require equivalent explicit preparation; profile membership lives in `tests/qualification-profiles.json`.
- `check:client` and several other checks build fixtures/generated assets and may invoke overlapping subchecks. Preserve their intended scope, but do not infer extra coverage from repeated execution.
- `check:context` is scripted deterministic memory qualification, not packaged live evidence. `check:quality` tests the quality harness; it does not automatically run an independent live-model comparison.
- `check:performance` distinguishes portable invariants from matched-hardware timings. `check:recovery` exercises real process recovery with a fixture backend, not a particular real GPU/model.
- Cloud typecheck/audit is not deployment isolation certification. Accessibility automation is not the full human keyboard/screen-reader pass.

### Build and packaged startup checks

Production, on the corresponding native platform:

```sh
npm run dist:release:mac -- --publish never
npm run dist:release:win -- --publish never
node scripts/check-packaged-app.cjs --auto
```

Eris-Dev, on the corresponding native platform:

```sh
npm run dist:dev-app:mac
npm run dist:dev-app:win -- --publish never
```

The macOS Dev command currently produces an application directory; distribution readiness requires resolving DIST-03. Production packaged smoke is a startup/preload/isolation probe. It is not the installed full interaction suite, a notarization check, a real-model coding run, or an update test. Retain separate evidence for those stages.

### Mandatory strict release evidence

The existing verifier reads exactly two JSON platform reports, each no larger than 16 MB, from `out/qualification/release-evidence` by default. Generate authentic reports through the qualified measurement workflow before running:

```sh
npm run check:context:release
```

Expected result: `out/qualification/context-release-verification.json` with `pass: true` and no failures, bound to the checkout SHA. The release workflow consumes `ram-context-release-evidence` from an explicit evidence workflow run and preserves a `context-release-qualification` declaration. Missing matched profiles, changed source, missing live evidence, different platform model weights/corpora or incomplete workload coverage must fail.

There is no claim here that a complete operator-friendly evidence producer already exists. If report generation, trusted upload or packaged measurement orchestration is incomplete, implement it under CERT before attempting v1 publication. Do not manually invent reports or bypass the policy. Signing, publication and tag operations are separate controlled release actions, not ordinary test commands.

### Real-model evaluation record

Freeze a representative task corpus and rubric before testing. Include coding, design, ordinary conversation, multi-turn corrections and model-specific protocol behavior; classify unsupported tasks explicitly. Keep model weights/hash, backend/runtime fingerprint, sampling settings and fixture hashes fixed within a paired experiment. Record actual requests sent, tool calls, final artifacts, verifier outcomes and infrastructure failures.

For the 10,000-question file, separately report imported, compiled, dispatched, answered, independently evaluated, passed, failed, cancelled and skipped counts. Chunking into batches of ten changes scheduling, not denominators. A complete routing replay does not establish 10,000 live answers; a complete live run does not establish 10,000 correct coding artifacts. Broader task-quality thresholds beyond the configured context gate must be selected and approved before RC testing, with failure categories and non-regression comparisons preserved.

### Phase 3 — Implement only the selected memory/extension scope

If large RAM tiers ship, deliver the bounded memory-process boundary before hardware auto-sizing. If durable journals, summaries, facts or specialist pulls ship, establish source identity, revocation, retention and recovery before exposing them. Keep embeddings/KV optimizations disabled until measured benefit and correctness are established. Cloud v2 support and image backends need separate explicit enablement gates.

### Phase 4 — Qualification and performance calibration

Run deterministic CI, production-boundary replay, full packaged UI journeys and independent live artifact checks. Populate real context hardware profiles and run exact-source paired/hardware reports. Complete long-session/low-memory and platform process-cleanup probes. A failed safety invariant blocks further promotion.

### Phase 5 — Release candidate and installed acceptance

Freeze the source/model/runtime identities, build signed/native artifacts and test fresh install, supported upgrades, updates, model discovery and support export. Rerun affected evidence after any fix. Publish only after strict 1.x context certification and final signoff; retain a tested incident/feed-pause/repair plan.

Dependency rules: A2A scoped handles depend on origin/evidence policy; durable journal reads depend on retention and source validation; large auto RAM tiers depend on safe storage/accounting; KV reuse depends on native support and invalidation, not merely a stable prefix; real-model grading depends on frozen fixtures/rubrics; publication depends on exact-source certification and installed distribution evidence.

### Release signoff checklist

- [ ] **SIGN-01 — Scope owner:** every applicable coding ID has a disposition and evidence; optional deferrals are enforced, documented and linked to follow-up issues.
- [ ] **SIGN-02 — Agent owner:** core task understanding, actual coding changes, bounded recovery, model policy and truthful outcomes pass the representative production-boundary and live scenarios.
- [ ] **SIGN-03 — Memory owner:** required context, origin/revocation, canonical history, pressure handling, child integration and supported journal lifetime meet their invariants.
- [ ] **SIGN-04 — Security owner:** no unresolved stop-ship authority, disclosure, credential or shipped-vulnerability findings; enabled remote/extension boundaries are qualified.
- [ ] **SIGN-05 — QA owner:** exact candidate CI plus full packaged interactions and independently graded real-model evidence pass with explicit denominators and no required skipped stages.
- [ ] **SIGN-06 — Hardware qualification owner:** complete matching macOS/unified and Windows/dedicated reports satisfy the existing strict release evaluator and calibrated performance budgets.
- [ ] **SIGN-07 — Distribution owner:** intended artifacts are signed/verified, install/upgrade/update paths pass, provenance/feed metadata is correct, and Eris-Dev cannot contaminate production updates or profile data.
- [ ] **SIGN-08 — Support/product owner:** current user/design docs, known limitations, troubleshooting/export flow and incident procedures match the binaries.
- [ ] **SIGN-09 — Release lead:** final tag/source/lock/artifact/evidence identities agree; no intervening change invalidates qualification; release and recovery owners explicitly approve promotion.

A v1.0.1 release is ready only when the final evidence demonstrates these obligations on the actual shipped scope. This document is the work plan for reaching that state, not a declaration that the state has already been reached.
